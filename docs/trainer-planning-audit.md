# Trainer planning audit — 2026-11-09

## Existing architecture and routes
- Web: React 19, Vite 6, TypeScript, Tailwind utilities loaded by the existing HTML shell. `/console` mounts TenantConsole; its role-gated CoachingConsole provides dashboard, athletes, programs, reports and messages as tabs. Existing identity selects the tenant and token. Dark slate cards, green/lime accent, rounded inputs and 48px controls form the current design language.
- Backend: FastAPI/SQLAlchemy in tenant_console.py and coaching.py; shared Supabase identity, current active tenant staff and explicit CoachLink authorization. `/api/console/coaching`: overview, dashboard, library, plans create/edit/assign/versions, workouts commands, reports, messages, wellness, equipment. Owner/admin privileges alone do not expose private training.
- Native Expo: coach, athletes, athlete, plan-setup, plan-builder, plan-versions, coach-reports, progress, drawer/plans and workout/[id]. ExerciseSelector, KeyboardFrame, MemberWeek, TodayProgram, coaching-store and offline command queue already implement member scheduling, manual/NFC recording and progress. Native uses a drawer/bottom navigation and focused screens; web wraps controls but currently retains long form layouts on phones.

## Capabilities to retain
102 authored library exercises, measurement-aware targets, superset/notes, starter programs, idempotent plan UUIDs and assignment request UUIDs, independent assigned copies, version concurrency checks, immutable workout snapshots, future-only assigned-plan changes, explicit coach/member relationships, consent-aware wellness, report review and messages. Existing NFC and five-second activity confirmation, quantities, extra sets and offline workflows must remain unchanged.

## Limitations and missing behavior
Web dashboard and member list share the same cards; no dedicated workout-template destination. Program creation uses repeated dates and a long form, not independent week slots. No explicit draft/publish/archive lifecycle, rest-day markers, duration/status/goal search filters, calendar preview, day/week copying or accessible down/duplicate controls. Assignment has no overlapping-program confirmation. Program and workout concepts are conflated in the editor. Existing actual-set reports are real but extra-set reporting needs prominent presentation.

## Data/API implications
Plan content is versioned JSON. Add optional lifecycle and rest_dates fields with legacy defaults (`published`, empty), preserving existing clients and published plans. Drafts can have no scheduled days, but publishing requires valid workouts. Assigned copies remain published and immutable through today. Add an independent owner/tenant-scoped workout-template table with optimistic versions and idempotent creation. Provide an additive PostgreSQL migration with RLS enabled and browser roles denied direct writes. Keep new endpoints behind current trainer staff validation. Explicit overlap acknowledgement retains both programs; never replace history.

## Proposed implementation
Reuse the existing authenticated CoachingConsole container, its API transport and member/report/messages functionality. Replace its program tab content with a responsive calendar/library/workout workspace; add a Workouts tab and dashboard action metrics. Use single-day selection on phones, desktop calendar and editor/library/summary panels, explicit save and leave confirmation. Rest days and unconfigured days remain different. Add program preview and member assignment search/summary. Surface actual versus prescribed sets and extras in existing member detail. No duplicate routes, no changes to NFC implementations or administrative access.

## Tests and environment
Python unittest suites exercise real disposable SQLite transactions with mocked identity provider; coaching and PostgreSQL RLS suites already exist. Native node:test suites transpile shared TypeScript and test offline, coaching, scheduling, NFC and role behavior. Web has a legacy API authorization test; no web lint script exists. Full web TypeScript has known legacy errors documented in TEST_ACCOUNTS.md. Browser verification will use a disposable local API database and deterministic test identities (test harness only), not production member data or auth changes. In-app browser discovery returned no browsers; standalone Playwright fallback is required. Physical NFC and actual iOS/Android software keyboards cannot be verified in desktop emulation.

## Follow-up review — mobile focus and publication completeness
The first delivered screenshots showed long mobile builders, repeated trainer headings, horizontally hidden main destinations, member details mixed with other members, and publication accepting sparse schedules without showing empty weeks. Refinements keep the same routes, authorization, schema and APIs: use responsive disclosure panels, a focused mobile editor with an explicit return action, a two-row library navigation, measured action-bar clearance and VisualViewport handling, selected-member summaries/direct future-plan opening, and a coverage review that requires explicit acknowledgement of unconfigured dates before web publication. Fully configured training/rest weeks should publish without an extra warning. Real-device checks require separate evidence; paired-device discovery alone is not an executed Safari/NFC test.
