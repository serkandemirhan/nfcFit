# NFCFit club roles and permission matrix

Updated 2026-11-08. This is the current product contract; the migration and acceptance reports below explain compatibility and release status.

NFCFit is club B2B SaaS. The only product roles are PLATFORM_ADMIN, CLUB_ADMIN, CLUB_MANAGER, TRAINER, and CLUB_MEMBER. There is no independent athlete account tier or consumer subscription. “Athlete” in existing schema/API identifiers describes a member participating in training, not an additional role. A member can maintain personal plans within an active club membership.

| Action | PLATFORM_ADMIN without club staff grant | CLUB_ADMIN | CLUB_MANAGER | TRAINER | CLUB_MEMBER |
| --- | --- | --- | --- | --- | --- |
| SaaS overview, create/suspend club, platform subscription approval | Yes | No | No | No | No |
| Club operational dashboard | No | Assigned club | Assigned club | No | No |
| Billing profile, subscription usage, upgrade request | No through club API | Assigned club | No | No | No |
| Club settings, operational audit log | No through club API | Assigned club | No | No | No |
| Invite/create/deactivate/remove Club Managers | No | Yes | No | No | No |
| Grant/revoke Club Admin | No | Verified target; last-admin protection | No | No | No |
| Invite/create/deactivate/remove Trainers | No | Yes | Yes | No | No |
| Invite/add/review/deactivate/remove Club Members | No | Yes | Yes | No | No |
| Register/assign/edit/revoke/remove NFC cards | No | Yes | Yes | No | No |
| Manage equipment and club exercise catalog | No | Yes | Yes | No | No |
| Browse exercise library | Authenticated library access, not member data | Yes | Yes for equipment/catalog work | Yes | Yes |
| Assign Trainer to member | No | Yes | Yes | No | No |
| Coaching dashboard, create club plan templates | No | Yes | No | Yes | No |
| Assigned member plan/performance/reviews/feedback | No | Active explicit Trainer assignment | No | Active explicit assignment | Own records |
| View unrelated members' private training records | No | No | No | No | No |
| Read another member's wellness | No | Explicit assignment + metric-specific consent | No | Explicit assignment + metric-specific consent | Own records only |
| Own plans, goals, history, wellness, permitted tracked edits | Only if separately a club member | If separately a member | If separately a member | If separately a member | Yes |
| Record NFC activity / start new club workout | Separate active club membership required | Same | Same | Same | Active membership |
| Access another club by changing tenant ID | No implicit access | No | No | No | No |

Club Admin has full operational authority, not an exemption from protected training/wellness access. Club Manager is an operations role, not automatically a Trainer. Platform Admin manages subscription policy through `/platform/*`, without receiving club staff permissions. A platform administrator with an explicit staff record can separately switch into that authorized club workspace.

Role resolution is per `(tenant_id, account_id)` staff row; memberships are separately club-scoped. One user can manage club A, train in club B, and be a member in club C. UI selection must never combine one club's role with another club's ID. Inactive staff/club rows confer no authority.

## Compatibility and ownership

Stored `owner` resolves to CLUB_ADMIN, `admin` to CLUB_MANAGER, and `coach` to TRAINER. They are legacy aliases, not additional product roles. Existing rows and histories are not rewritten. `/auth/me` and staff responses retain the stored `role` for compatibility and add `effective_role`; updated clients normalize both forms. Updated client writes use canonical roles. Legacy aliases remain accepted at the API boundary with identical permission checks. New platform-provisioned clubs receive CLUB_ADMIN.

A Club Admin invitation is provisioned initially as Manager/Trainer. The target must sign in with a verified email before an existing Club Admin can promote them. Staff mutations serialize on the club row and re-check current actor/target roles. The last active Club Admin cannot be demoted, suspended, removed or deleted, including simultaneous database requests. Ownership handoff requires promoting a verified successor first, then revoking the former administrator. No emergency platform impersonation or last-admin bypass endpoint is introduced.

Removal means access revocation (`removed`), not deletion of the account, workouts, versions or plan history. Card deletion retains activity records. Invitations provision an email-bound account/club relationship; they do not send an email automatically.

## Enforcement and evidence

Frontend navigation, protected native routes, API guards and PostgreSQL read policies all enforce tenant scope. Direct authenticated database mutations are denied; writes use checked backend transactions. Server roles are re-read on requests. Existing offline navigation can use cached identity; unseen revocations cannot take effect on an offline phone until synchronization. Rejected offline recordings remain visible.

Staff invitations/transitions, membership invitations/reviews/transitions, NFC revocations/removals, billing-profile changes and subscription requests/reviews create transactional audit entries. Tax identifiers and billing addresses are not copied to audit details. PostgreSQL prevents audit alteration.

See [migration plan](NFCFIT_CLUB_ROLE_MIGRATION.md), [screen inventory](NFCFIT_SCREEN_INVENTORY.md), and [pre-pilot acceptance report](NFCFIT_CLUB_ROLES_ACCEPTANCE.md).

## Pre-pilot review applied to both administrative panels

- Separate section navigation for overview, members, NFC cards, catalog, staff and operational activity. Subscription/settings/billing/audit only appear for Club Admin.
- Manager Trainer assignment stays in staff operations; no detour into a protected coaching workspace.
- Native selectors remove suspended clubs/staff and filter operators; web selectors remove inactive grants. Changing tenant/role remounts the relevant scoped console to avoid retaining another selected club's UI state.
- Search for member/card lists, compact section controls and existing card details sheet retained.
- Destructive member/staff removals have confirmation and preserve historical records. Role changes have explicit role labels; the server explains last-admin/verified-successor failures.
- Forms report errors and save state. Admin subscription requests remain pending until platform approval; approved capacity is explicit and cannot be below current usage.
- Native Admin subscription form and web Admin billing form do not expose payment collection implementation details as a user action. Platform-managed billing is explained accurately.
- Empty/error/retry states exist for subscription/audit loading. Database or API permission failures are not interpreted as a successful save.

This is a source and functional permission review. Authenticated pixel/layout, keyboard, touch, screen-reader and physical-device checks of these newly changed panels remain pending because the connected browser was unavailable. Earlier Android screenshots describe earlier builds and are not evidence for this role release. See the acceptance report for current verified checks and external limitations.

# Club role compatibility and rollout plan

Date: 2026-11-08. Production data and deployments have not been changed by this implementation.

## Inspect first

Existing staff storage is a unique club/account row with `owner`, `admin`, `coach`; members are separate membership rows; platform administration is an account flag. Backend `_tenant_access` already required a scoped staff row, whereas some navigation and operational reads conflated responsibilities. Existing active Trainer assignments and granular wellness consent are preserved. Existing historical `actor_role` values describe the actor at the time; they must not be rewritten.

The explicit alias mapping is owner → CLUB_ADMIN, admin → CLUB_MANAGER, coach → TRAINER. Manager no longer inherits Trainer plan/performance access. Any previous coaching assignments belonging to a legacy `admin` remain in history but do not authorize Trainer reads while that account is a Manager. An authorized Club Admin must deliberately choose the appropriate role and reassignment if that staff member will now train members. No automatic role promotion occurs.

## Additive migration

`backend/migrations/20261108_club_roles.sql` adds billing profiles, subscription requests and immutable audit records. It adds accepted-role validation, a last-admin trigger, scoped base-console read policies and canonical-role support in coaching helper functions. It makes no UPDATE to stored roles and deletes no business data. It is transactional and was tested twice consecutively against an isolated PostgreSQL cluster.

The migration fails if an unexpected existing policy would combine with the new policy to widen access, or if unrecognized staff role values exist. Resolve discrepancies through an explicit reviewed mapping/policy decision rather than deleting or reclassifying rows automatically.

## Release sequence

1. Back up the target database and record schema/policy definitions and row counts. Explicitly select the target `DATABASE_URL` without printing it or committing environment files.
2. Run `backend/.venv/bin/python backend/scripts/check_club_roles.py`. It opens a read-only PostgreSQL transaction and reports role counts, clubs lacking an active admin and unexpected base-console policies. Resolve any reported exception before rollout. It sends no invitations and performs no migration.
3. Apply `20261108_club_roles.sql` as the schema owner after the existing coaching foundation migration. Runtime `create_all` alone does **not** install PostgreSQL security policies/triggers.
4. Deploy the backend with canonical/legacy compatibility before updating web/mobile clients. Run authenticated tenant-isolation, direct API denial and last-admin checks in staging. Test an existing legacy-role account and a canonical-role account, including distinct roles in two clubs.
5. Deploy web and distribute the updated Android build. Old clients can keep sending legacy aliases; new canonical roles may require the updated clients for navigation. A legacy Manager may still show an old Trainer entry but the new backend denies that access.
6. Verify Admin billing/settings/Manager controls and Manager operational-only controls in authenticated web and Android sessions. Confirm current plan/workout history, offline queue replay and revoked membership handling. Acceptance must record the exact deployed builds, not infer production success from local tests.

## Rollback and limits

Keep the additive tables, protected ledger, role aliases and policies during an application rollback. Do not roll back to an API that does not understand canonical roles or that restores Manager coaching authority. Restore a compatible application release, or forward-fix permissions. Do not drop the audit/last-admin guards as a routine rollback.

If a club has no active administrator before migration, the trigger cannot invent a secure owner. Resolve ownership using a verified business ownership process before rollout. To transfer a functioning club, have the verified successor sign in, promote them to CLUB_ADMIN, then revoke the former admin. Do not remove the sole admin first.

Billing profiles and platform-reviewed subscription changes work without a payment provider. Automated payment collection, card management and invoice downloads require a configured provider/integration; no charged payment or generated invoice is claimed. Staff/member “invitations” are provisioning operations and do not currently send email.

# Club roles — pre-pilot acceptance report

Date: 2026-11-08. Scope: the existing Android application, web club console, FastAPI authorization and PostgreSQL policies. This is a local implementation/acceptance report, not evidence that production has been migrated or the changed panels installed on a phone.

## Delivered behavior

- Five product roles with tenant-scoped grants and explicit legacy compatibility; no independent athlete tier or consumer subscriptions.
- Club Admin: operational dashboard, Manager/Trainer/member controls, verified Admin promotion, subscription usage/change requests, billing profile, club settings and audit log.
- Club Manager: members, Trainers, cards, equipment, catalog and Trainer/member assignment. No billing/settings/Manager/Admin controls or inherited Trainer access.
- Trainer: library, club templates, assigned-member plans/performance/reviews/feedback. Changing Trainer to Manager revokes coaching access on the next request, including old owned club templates; historical records remain stored.
- Member: own plans, goals/history/wellness and permitted tracked changes; new personal plan creation requires an active club membership. Existing histories remain readable by their owner.
- Platform Admin: platform subscription/tenant endpoints; no automatic club operations/coaching authority. An explicit scoped staff grant is honored independently of the platform flag.
- API and database last-admin protection, including concurrent removal; verified successor promotion before ownership handoff.
- Transactional invitation/role/membership/card/billing/subscription audit entries and an immutable PostgreSQL audit ledger.

## Automated acceptance

Final results are recorded in `artifacts/club-roles-2026-11-08/checks/`, including the exact command and exit status for each check. The standalone HTML report embeds these logs and source hashes.

| Check | Result |
| --- | --- |
| Backend API/domain journeys, both legacy and canonical role fixtures | PASS — 57 executed; 4 PostgreSQL cases skipped here and executed separately |
| Isolated PostgreSQL RLS/migration tests | PASS — 4 real PostgreSQL cases, including concurrent last-admin removal and populated migration reapplication |
| Native regression suite, including web/native capability parity | PASS — 99 tests |
| Mobile TypeScript and targeted ESLint | PASS — no TypeScript errors; targeted ESLint has zero errors/warnings |
| Web TypeScript and production build | PASS — no TypeScript errors; Vite production build completed |

The backend discovery command skips PostgreSQL cases unless pointed at an isolated database. The PostgreSQL runner executes those cases separately in a disposable socket-only cluster; it never uses the app database.

### Allowed/forbidden scenarios covered

1. Each role against operational reads and mutations; Admin/Manager catalog/equipment/assignment writes and forbidden Trainer/Member/Platform writes.
2. Admin-only subscription, billing-profile, settings and audit access; Manager direct-call escalation/self-promotion denied, including legacy aliases.
3. Different roles in different clubs, role-specific club navigation, cross-club record-ID substitution and platform flags without staff grants.
4. Manager can create/change/revoke Trainers, but cannot grant or change Admin/Manager access. Removed account/history rows are retained.
5. Sole Admin suspension/removal/demotion denied; two verified Admins permit ownership handoff; unverified successor promotion denied.
6. Concurrent database removal of two Admins leaves exactly one active Admin.
7. Direct authenticated SQL writes/password-hash reads denied; Admin billing/audit reads and Manager denials; Trainer privacy and granular wellness consent tested with both stored role generations.
8. Club role downgrade removes template/performance access without deleting plan rows.
9. Idempotent migration reapplication, accepted legacy rows preserved and unexpected permissive policy rejected transactionally.
10. Member invitations/reviews/removals and card revocations/removals leave auditable results. Billing profile logs contain field names, not tax IDs/addresses.
11. Subscription approval requires Platform Admin and explicit capacities; rejection leaves the current plan unchanged; a Club Admin cannot grant themselves limits through platform endpoints.
12. Existing manual/NFC recording, durable SQLite queues, retry/idempotency, partial sets, session date handling, plan snapshots/history and local progress regressions remain in the mobile/backend suites.

## Administrative UX audit

The [screen inventory](NFCFIT_SCREEN_INVENTORY.md) records both panels' section placement, restricted controls, role labels, member/card search, loading/error/retry states, destructive confirmations, verified-successor errors and subscription request feedback. Trainer assignment was placed in operational staff management so a Manager does not need to open the Trainer area. Equipment management is available in web operations as well as native operations.

Authenticated visual/interaction acceptance of the changed panels remains **pending**. The browser runtime returned no connected browsers. No screenshots from previous APKs are reused as current evidence. Keyboard, Samsung system navigation, touch targets, screen reader behavior and real network timings require the changed build on the physical device. No new Android APK was requested or generated for this role-only release.

## Release constraints and outstanding external work

- Production migration, deployment and authenticated staging/physical acceptance have not been performed. Follow the [explicit rollout/rollback plan](NFCFIT_CLUB_ROLE_MIGRATION.md); runtime model creation is not a replacement for PostgreSQL policy migration.
- Billing profile edits, usage and platform-reviewed subscription changes are implemented. Automatic charges, payment-method changes and invoice downloads require a configured payment provider; the UI does not claim these exist.
- Staff/member invitations provision relationships bound to verified-email sign-in. Automatic invitation email delivery is not configured and no real invitations were sent during tests.
- An offline phone cannot instantly learn an unseen membership/staff revocation. Current server checks apply on reconnection; no offline queue/history is silently erased.
- Existing production legacy fitness tables/policies were not rewritten by this scoped console migration. Their historical owner policies remain a separate baseline, not an inferred result of these isolated PostgreSQL tests.

Automated permission acceptance may pass while visual/release acceptance is still pending. This report does not declare an unconditional pilot go-live.
